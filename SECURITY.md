# Security policy

## Scope

dsh-tailscale-serve is a transport helper: it forwards TCP from a Tailscale
address to the loopback DSH port and optionally publishes a tailnet-only
`*.ts.net` name. It intentionally does **not** authenticate anyone.

## Guarantees enforced in code

1. The listener can only bind an address inside `100.64.0.0/10` or
   `fd7a:115c:a1e0::/48` (Tailscale). `0.0.0.0`, LAN and public addresses are
   refused unless `allowNonTailnet: true`.
2. If `pairingCheck` is not `"off"` and `/pair-app` does not answer with a 200
   HTML shell, no listener is started (fail closed) unless
   `allowUnpaired: true`.
3. `allowedPeers` entries are parsed strictly: malformed entries never widen
   access, and an empty list means "every device on the tailnet".
4. No token, cookie or credential is stored, logged or generated by the plugin.

## Threat model and limits

| Threat | Covered? | Notes |
| --- | --- | --- |
| Port scan from the public internet | yes | nothing is exposed outside the tailnet |
| Other LAN devices reaching DSH | yes | never binds a LAN address |
| Random device on your tailnet | only with `allowedPeers` | default tailnet ACL is often allow-all |
| Compromised tailnet account / coordination server | no | control plane can authorise new devices |
| DSH pairing plugin misconfiguration | no | the plugin is gate-agnostic by design |
| Stolen phone holding a long-lived pair cookie | no | revoke the device in the pairing plugin |

## Hardening checklist

- Keep `allowUnpaired: false` and `pairingCheck: "auto"`.
- Set `allowedPeers` to the exact tailnet IPs you use (e.g. one phone).
- In the Tailscale admin console: enable device approval, require MFA on the
  account, and write an ACL that only allows `phone -> this machine:8081`
  (plus `443` if you use `serve`).
- Prefer short token lifetimes in your pairing plugin over convenience.

## Reporting

Open a private advisory on GitHub, or mail the maintainer listed in
`package.json`. Please do not file public issues for vulnerabilities.
